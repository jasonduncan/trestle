# ADR-006: Historical schema format and migration SDK

**Status:** Accepted (M3, 2026-09-26) · **Design doc:** §13–§14, §19.2 C, I07, I08, I10 ·
**Amended by:** ADR-017 (fence migrations), ADR-019 (preconditions, impact, drift), ADR-020 (batched data steps), ADR-021 (online changes), ADR-023 (scalar columns)

## Context

M0–M2 used hand-written SQL migrations with a digest-checked ledger. M3
needs Django-style `makemigrations` without a whole-program macro, while
keeping three states distinct: desired (D), historical (H) and observed (O).

## Decision

- **Schema IR** (`trestle_historical::schema`): models and fields have
  stable IDs (`lessons.lesson`, `lessons.lesson.title`) that are separate
  from table and column names. Presentation is not part of it, so a label
  or widget change can never produce a migration.
- **D**: apps declare `Model`s with an explicit builder (the design's
  "explicit equivalent" of a derive) via `app.model(..)`. Assembly checks
  namespaces and requires a declared dependency for cross-app references.
- **H**: every migration artifact is a manifest (`<app>/<id>.json`) with
  logical `StateOp`s plus its SQL (`<id>.sql`). Replaying the ops yields H.
  Format 1 annotates pre-existing SQL, and its digest stays SQL-only, so
  already-applied history is untouched. Format 2 digests the manifest, the
  SQL and the data step's source.
- **O**: `verify` compares the catalog with H for the migrations the ledger
  records as applied: tables, columns, types, nullability, unmanaged
  columns, primary and foreign keys, and constraint and index names.
  Expressions are reported as unverified, never as a match.
- **Planner** (`makemigrations`):
  - Matches by stable ID, so renames are renames and a delete plus an add
    is never guessed to be one.
  - Blocks removals unless `--allow-destructive <id>` is given; the
    approval is recorded in the manifest.
  - Blocks required fields that have no default or backfill
    (`.backfill_with(value)` for a constant; `--filled <id>` after a
    committed data migration).
  - Blocks type, key, reference and default changes.
  - Assigns check names at creation and keeps them as history.
- **SQL rendering** re-validates every identifier and escapes every
  literal, even from committed artifacts.
- **Historical SDK** (`HistoricalTx`): data steps name models by stable ID
  and fields by key, resolved against H *at that migration*. The API is
  bounded batches by primary key, plus update, insert, delete and count,
  with bound parameters only. A data step runs in its migration's
  transaction.
- **Discovery:** `pilot-migrations/build.rs` registers every artifact.
  Manifests link data steps by name to `crate::data::<name>()`, so a
  missing step fails to compile.

## Evidence

- `crates/trestle-historical/tests/evolution.rs` (the §14.4 proof), with
  every migration generated by the planner:
  - release A (populated), B (add, data backfill, require) and C (rename
    the column and the table);
  - a fresh replay and an upgrade in place converge on the same catalog,
    including constraint definitions;
  - B's data step still replays after C's rename;
  - editing an applied data step is a digest mismatch;
  - a failing data step rolls back.
- `examples/pilot-migrations/tests/replay.rs`: the legacy manifests match
  the real catalog, and the legacy digests are unchanged (checked
  independently with `shasum`).
- `examples/pilot/tests/schema.rs`: models match history, a presentation
  change produces no migration, a removal is blocked, and a generated
  migration applies on top of the committed history and verifies. The typed
  columns match the model; the scoped list query filters, orders and
  bounds.
- Concurrent runners serialize (`trestle-historical/tests/runner.rs`, M0).

## Consequences

- Adding a column type means changing the IR, the SQL renderer, the verifier
  and the SDK together.
- Not generated: type changes, key changes, default changes, non-transactional
  steps (for example `CREATE INDEX CONCURRENTLY`), and merges of branched
  histories (detected; merge by hand).
- Web startup still checks only the declared schema requirements and never
  applies migrations. `pilot schema verify` is an operator check.
